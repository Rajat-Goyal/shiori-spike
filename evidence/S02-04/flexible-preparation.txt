S02-04 — Flexible preparation conversations
Verified: 2026-07-30 (Asia/Singapore)

Contract and bound
- Existing product validators establish a positive bounded work-session duration of 1–1440 whole minutes.
- Work-session starts retain the existing 30-minute Singapore-time granularity.
- Ends are derived from duration, so a 45-minute session may end on :15 or :45.
- Telegram remains the mutation surface; the dashboard remains read-only; Google Calendar is read-only.

Acceptance evidence
AC1 — Mandatory preparation decision and exact focus
- Every newly complete promise still enters offer_help before creation.
- The agent preparation tool requires the exact focused draft id, version, complete phase, possible-work-session mode, and durable preparation stage.
- ConversationService hands the validated input to WorkSessionFlow without applying a generic draft mutation or changing focus.
- Ordinary-question behavior continues to preserve the active draft and pending question.
- Ambiguous two-draft resolution is terminal decision-only: mutation tools are disabled, focused fallback authority is unavailable, all model-supplied mutation payloads are discarded, and ConversationService persists one clarification before any domain call.

AC2 — Flexible bounded durations, including 45 minutes
- Decision/runtime, scheduling, repository, dashboard, work-session, and approved-edit validation accept integers from 1 through 1440.
- Unit coverage verifies a 45-minute option beginning at 08:00 and ending at 08:45.
- Cross-midnight and full-day (1440-minute) windows preserve their exact duration.
- Application and database boundaries enforce the same Singapore-local :00/:30 start rule and exact end = start + duration invariant.
- Database coverage verifies 45- and 1440-minute persistence and rejects a :15 start.
- Dashboard parsing rejects zero, fractional, over-bound, and duration/window-mismatch rows.
- The same validation is applied to dashboard session history; tests reject 0, 1441, fractional, mismatched, and :15-start rows while accepting exact 45-minute and cross-midnight 1440-minute rows.

AC3 — Natural constraints and owner-selected times in one durable run
- propose_work_session_input is part of the same Agents SDK run as the typed owner turn.
- Durable agent product context includes only structured preparation stage, duration, canonical constraints, and selected start/end.
- The agent translates natural constraints to the existing canonical Singapore format and owner-selected time to an exact future +08:00 start.
- WorkSessionFlow performs the authoritative availability check and transition.
- Explicit duration and timing facts included in the original commitment message are applied immediately after draft creation in the same run.
- The deterministic guard accepts only explicit complete commitment input and does not infer preparation from unrelated phrases.
- A submitted preparation duration must occur exactly in preparation/work-associated text or as an unambiguous preparation-only phrase; numeric occurrences in relative target phrases (`in`, `within`, or `after N minutes`) are excluded.
- Tests reject 45 as preparation in “due in 45 minutes … need 15 minutes to prepare” before accepting the exact 15, and reject borrowing 45 from “Submit in 45 minutes; I need to prepare” before asking for the missing preparation duration.

AC4 — Controlled Calendar outcomes
- Free generated windows use application-owned sanitized choice copy.
- Free owner time reaches confirming.
- Busy owner time reaches conflict_choice with application-owned conflict copy.
- Provider failure/unavailable reaches availability_unavailable or unverified_confirming with application-owned warning and explicit actions.
- Tests assert replies contain no title, attendee, description, event, or provider detail.

AC5 — Declining preparation
- Natural no-preparation input calls the deterministic decline transition for the exact draft/version.
- The resulting new version is passed immediately to the existing same-session creation-approval continuation.
- No commitment is created before the owner approves the exact consequence.

AC6 — Flexible continuations
- Natural typed continuation duration is authoritative for the exact referenced active intent and accepts 1–1440 whole minutes.
- Context exposes only owner-isolated active continuation intent references and state.
- Database transition and final confirmation enforce the same duration and exact-window bounds.
- Database coverage verifies the 45-minute outcome → options → explicit confirmation path creates exactly one session and two messages.
- The continuation transition locks and consumes the authoritative claimed Telegram row in place. A linked model-decision audit remains byte-for-byte attached to that update through the natural 45-minute transition, which advances the intent exactly once; replay through a new repository instance is inert.

Safety and durability
- Additive migration only; no prior migration was edited.
- Typed preparation and continuation outcomes terminally finalize claimed Telegram updates for applied, stale, expired, unsupported, invalid, unavailable, no-fit, provider-failure, domain-error, replay, and restart paths.
- Typed finalizer failures propagate to the Telegram boundary instead of producing normal success copy; the outer boundary records terminal failure and suppresses replay.
- Same-message preparation consumes the exact processed creation turn in place without deleting its Telegram row or linked model-decision/draft-operation audit history.
- Stale draft versions remain inert.
- Availability transitions store at most two sanitized windows.
- Commitment confirmation still creates at most one next work session.
- No Google Calendar write path was introduced.
